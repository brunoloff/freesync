# Initial synchronization policies

The preview includes ordinary hidden files. Exclusion globs match relative paths and apply recursively to excluded directories. Excluded contents are not deletion authority. Symbolic links, special files, non-UTF-8 names and names containing path separators or colons are skipped or reported as unsupported; they are not followed or silently renamed.

Each folder pair defaults to **Respect .gitignore**; old saved pairs default to enabled too. The Folder options checkbox can disable this policy and preview the newly included paths before sync resumes. Local `.gitignore` files apply to both uploads and downloads, including paths present only on Drive. Anchored and directory rules, nested rules, and negations are supported; a child cannot re-include a path beneath an excluded parent. Repository case matching follows its `core.ignorecase` setting. Files recorded in the nearest repository's Git index and the folders needed to reach them remain included. A pair selected inside a repository inherits that repository's ancestor rules. Standalone `.gitignore` files work within a pair too. Git metadata itself is not excluded as a side effect of an ignore pattern. This option deliberately reads `.gitignore` files, rather than machine-specific global Git excludes or `.git/info/exclude`.

Exclusion leaves both sides untouched, retains existing baselines, and cancels queued work without creating deletion authority. Current rules are checked before writes and upload chunks; parent deletions and moves cannot carry ignored descendants along with them. Ignore files and indexes are cached per inventory, with changes invalidating that inventory. Watchers continue to observe rule changes, and periodic scans cover missed events. Unreadable rules or a corrupt tracked-file index stop sync instead of silently including more files. Disabling the option does not remove explicit folder exclusions.

The private remote-ignore audit script classifies a saved adoption metadata snapshot using the local Git rules and tracking index. It records paths, opaque Drive IDs, versions, sizes and matching rules for later review, with unknown tracking status and machine-specific exclusions kept separately. Folder matches are not approval for recursive deletion. Its coverage summary records missing local rule files, unmapped metadata, changed rules and failed repository checks. The audit performs no cloud requests or deletions; any later cleanup requires fresh ID/version/rule checks and separate user authorization.

Local roots must be real directories and must not overlap another pair or application state. A scan error, unavailable root, changed root identity or incomplete Drive listing blocks reconciliation. Drive duplicate names remain explicit ambiguities. File equality uses content checksums and sizes; timestamps alone do not establish a baseline.

Filesystem changes request a rescan. Read/access notifications and changes to sibling folders are ignored, so inventory reads cannot feed back into repeated scans. Native watching uses a short bounded debounce; periodic reconciliation also runs when no event arrives. Native watcher errors and rescan warnings invalidate the inventory, while scan recovery covers missed events. A missing root is not an empty inventory. Parent monitoring and periodic scans detect its return, after which root identity must still match the established pair.

Normal synchronization uses Drive trash and retains local deleted/replaced contents in profile recovery storage. It never permanently deletes Drive files. The retention policy for the initial preview is to keep local recovery copies until the user removes them; no automatic cleanup is enabled.

Explicit Use local and Use Drive conflict choices also retain the displaced original in recovery. Each instruction records the displayed versions and executes on the sole sync owner; changed content or file identity rejects an obsolete choice. Instructions for other conflicts can be queued during preparation or transfer. Keep both retains both names. Diff leaves the conflict unresolved and opens private, read-only snapshots rather than writable synchronized originals. Full text validation accepts UTF-8 and BOM-marked UTF-16; binary content fails with a visible explanation.

The initial preview requires sync, staging and recovery storage on the same filesystem for local replacements/deletions. Cross-filesystem moves fail visibly before removing the source. Local installation creates a file only if the destination is absent; an intervening editor save is preserved. A failed transfer's staged source/download remains available for recovery. Conflicts remain visible until explicitly resolved, while unrelated paths continue syncing.

Automated development writes are limited to the explicitly mapped `test-freesync` local and Drive roots. Phase 8 adoption inventories the existing InSync tree read-only. Activating a reviewed subfolder requires a finished report, fresh content and ancestry checks, consistent backups, and a root-bound approval receipt. Matching content retains its Drive IDs without transfers; initial differences remain conflicts. Overlapping pairs are rejected. Completing adoption implementation does not activate the real tree. Google-native documents, shortcuts and existing link files stay protected; complete link-file behavior and portable filename mapping are Phase 9 work.

The private profile stores durable Activity history in SQLite and mirrors it to `activity.jsonl`: authored events, relative file paths, sizes, operation/decision IDs, recovery locations, attempts, retry times, scan durations/counts and typed error codes. `events.jsonl` remains a count-only engine summary. Neither log includes file contents, credential values, OAuth URLs or upload-session objects/URLs. JSON logs rotate after 2 MiB, retaining one previous file. SQLite history is retained across restarts without automatic pruning; storage budgeting remains part of Phase 10. History starts with the new logging version; past transfers are not fabricated.
